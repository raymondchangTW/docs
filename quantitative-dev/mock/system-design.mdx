Trading system design rounds ask you to reason about latency budgets, deterministic behavior, fault tolerance and risk controls, which generic web-scale prep does not cover. This page has eleven design questions with follow-ups and answer points. The answers are principles, not code.

<Info>
  **Status of this page.** Last checked on 15 November 2026. These are general practice frameworks, not any firm's interview content or technology stack. Latency and throughput figures vary by firm tier and are deliberately left out.
</Info>

## A framework for any trading design question

1. **Clarify scope:** exchange side (matching engine, order book) or participant side (market data handler, strategy, order management, risk)? Which latency tier: microseconds, milliseconds, or minute bars?
2. **List requirements:** functional needs, latency and throughput targets, correctness guarantees (never lose an order, never double-process a fill), and failure behavior.
3. **Sketch components and data flow,** then deep-dive on the hardest part.
4. **Cover failure modes:** crashes, gaps, duplicates, slow consumers, bad data, operator error.
5. **Cover observability and safety:** monitoring, replay, limits and kill switches.

## Market data and research platforms

<AccordionGroup>
  <Accordion title="Q1. Design a market data ingestion and storage system for ETF, stock and futures prices used by both research and live pricing.">
    **Clarify requirements first:** latency needs (live quotes or end-of-day research), data volume, number of sources, retention period, and who the users are.

    **Architecture:**

    - **Ingestion layer:** One adapter per source, normalizing each vendor format into one internal schema (symbol, UTC timestamp, quote, trade, source, receive time). Keep raw data immutably.
    - **Real-time path:** A low-latency message queue or stream feeding the pricing and risk services. Handle out-of-order data, duplicates, disconnects and backpressure.
    - **Historical storage:** Time-series or columnar storage partitioned by date and symbol. The real-time path writes continuously, and a batch job later recomputes and reconciles.
    - **Quality and monitoring:** Automated detection and alerting for gaps, stale data, outliers and latency.

    **Follow-up:** How does research avoid getting data that was only known later?

    → Record both event time and receive time, and query point-in-time when models read data. Keep versions of corrected data and never overwrite old values. See [Data engineering](/quantitative-research/interview/data-engineering).
  </Accordion>

  <Accordion title="Q2. Design a market data distribution system for several strategies on the same machine or network.">
    **Core pieces:** feed handlers that decode exchange messages, an in-memory order book per instrument, sequence gap detection, and a fan-out layer that publishes normalized updates to consumers.

    **Design points:**

    - **Redundant feeds:** Consume two copies of the same feed and arbitrate by sequence number, so a dropped packet on one line is covered by the other.
    - **Gap recovery:** Track sequence numbers per channel. On a gap, request a retransmission or a snapshot, and mark the affected book as uncertain until it is repaired.
    - **Fan-out:** Decide between latency and flexibility. Shared memory or multicast gives the lowest latency, while a message bus is easier to operate. Slow consumers must not block fast ones, so use bounded queues and a drop or disconnect policy.
    - **Normalization:** One internal format with explicit time zones, price scaling and instrument identifiers.
    - **Replay:** Record the input stream so any session can be replayed for debugging and testing.

    **Follow-up:** What should downstream strategies do while a book is in an uncertain state?

    → Layer the defense: prevent gaps where possible, detect them quickly, recover, and in the meantime trade less aggressively or pause quoting for the affected instruments.
  </Accordion>

  <Accordion title="Q3. Design a backtesting framework. Event-driven or vectorized?">
    - **Vectorized:** Fast and simple to implement, suitable for signal research and daily-frequency strategies. The weakness is that path-dependent logic (stops, position limits, volume constraints) is hard to model.
    - **Event-driven:** Consumes events in time order (quotes, trades, order acknowledgements) and can share logic with the live system. It is more realistic but slower and more complex.

    A common approach is to use vectorized code to screen ideas quickly, then validate candidates with an event-driven run for costs and execution.

    **Design points:**

    - One time axis, and signals can only use data known at that time.
    - Pluggable cost models: spread, fees, borrow, slippage.
    - **Reproducibility:** Record code version, data version, parameters and random seed, so the same inputs give the same result.
    - Accurate replay of recorded market data, walk-forward validation, and reports with P&L attribution, not just a Sharpe ratio.

    **Follow-up:** How do you prevent look-ahead bias?

    → Enforce it in the architecture: strategies get data only through an interface that returns data before the current time. Add a test that deliberately corrupts future data and checks the results do not change. See [Regression and backtesting](/quantitative-research/interview/statistics-backtesting) Q8.
  </Accordion>

  <Accordion title="Q4. How do you bridge research code and production code?">
    The risk is that the research version and the production version of a strategy drift apart, so backtest results stop describing live behavior.

    - **Shared core:** Put signal and pricing logic in one library used by both research notebooks and the live system.
    - **Same data interface:** The strategy reads data through the same abstraction in backtest and live, with a replay source in one and a live feed in the other.
    - **Parity tests:** Run the live code path on recorded data and compare its decisions with the backtest output.
    - **Shadow mode:** Run new logic in production with real data but no orders, and compare it with expectations before enabling trading.
    - **Configuration, not copies:** Parameters live in versioned configuration, not edited copies of the code.
  </Accordion>
</AccordionGroup>

## Trading components

<AccordionGroup>
  <Accordion title="Q5. Design an in-memory order book and matching engine for one venue.">
    **Requirements to confirm:** order types (limit, market, cancel), matching rule (price-time priority), operations needed (add, cancel by order ID, best bid and ask, depth), and that the book fits in memory on one machine.

    **Data structures:**

    - Each side of the book is a sorted structure of price levels, so the best price is fast to read.
    - Each price level holds a first-in, first-out queue of orders, which implements time priority.
    - A hash map from order ID to the order's position allows cancellation without scanning the book.
    - Cache the best bid and best ask so top-of-book reads are constant time.

    **Matching:** An incoming order is matched against the opposite side, best price first and oldest order first within a price, producing trades until it is filled or no longer crosses. Any remainder rests in the book.

    **Follow-up 1:** Why do real engines often run the book on a single thread?

    → A single writer per instrument gives a deterministic, auditable sequence of events with no lock contention, and it keeps price-time priority simple to guarantee. Parallelism comes from partitioning by instrument, not from sharing one book across threads.

    **Follow-up 2:** Orders arrive on several network threads. How do you keep it correct and fast?

    → Funnel all inbound messages into one ordered queue (sequenced) that the matching thread consumes. Keep the hot path free of allocation, blocking calls and disk writes, and write the event log asynchronously.

    **Follow-up 3:** What happens if the engine crashes?

    → The event log is the source of truth. Replaying it into a fresh process rebuilds the book exactly, which is why determinism matters. Persistent trade records must stay consistent with the in-memory state.
  </Accordion>

  <Accordion title="Q6. Design an order management system (OMS).">
    The OMS turns trading decisions into exchange orders, tracks each order's lifecycle, and keeps its positions consistent with the exchange.

    - **Order state machine:** New, acknowledged, partially filled, filled, canceled, rejected, with explicit legal transitions. Illegal transitions are logged and alerted, not ignored.
    - **Idempotency:** Give every order a unique client order ID so that retries after a timeout cannot create duplicates.
    - **Concurrency:** Several strategies may submit at once. Serialize state changes per order, and enforce pre-trade limits atomically with submission.
    - **Reconciliation:** Compare internal orders and positions with the broker or exchange regularly and at startup, and treat the external record as the authority.
    - **Persistence:** Write every state change to a durable log so that a restart can rebuild the open order set.

    **Follow-up:** An acknowledgement never arrives after you send an order. What do you do?

    → Do not assume it failed. Mark the order as unknown, query the order status from the venue or broker, and only then resend or cancel. Blind resends are how duplicate orders happen.
  </Accordion>

  <Accordion title="Q7. Design a live pricing and hedging service for an ETF market maker. How do you make it safe?">
    **Functional breakdown:** market data input, fair value calculation, quote generation, inventory and risk, and hedge suggestions or execution.

    **Safety design:**

    - **Stale data protection:** If any input has not updated within a time limit, quotes automatically widen or are pulled.
    - **Sanity checks:** Reject quotes that deviate too far from fair value or show abnormal price jumps.
    - **Risk limits:** Hard limits on position, notional, order rate and order size.
    - **Isolation:** Keep pricing, execution and risk checks separate so one failing module does not take down the rest.
    - **Observability:** Monitor latency, rejection rate and position breaks, with alerts.

    **Follow-up:** How do you recover position state after a restart?

    → Treat fills as the source of truth (event sourcing, or rebuilding from execution reports). After a restart, reconcile with the broker or clearing positions first, then resume quoting. Do not rely on in-memory accumulated values as the only source. See [ETF and Delta-1](/quantitative-research/interview/etf-market-making).
  </Accordion>

  <Accordion title="Q8. Design the kill switch for an automated trading system. How do you make sure the kill switch itself cannot fail?">
    **Layers:** Use more than one level of control, for example per-strategy circuit breakers, a software control in the order management layer, and a control on the network path to the exchange.

    **Triggers:** P&L loss thresholds, position or notional breaches, error or reject rates, abnormal order rates, loss of market data, and manual action by an operator.

    **Actions:** Cancel open orders, block new ones, and optionally flatten positions under supervision. Define clearly who can reset it and how.

    **Making it reliable:**

    - Keep it independent from the code it protects, so a bug in a strategy cannot disable it.
    - Fail closed: if the kill switch loses contact with the system, the default is to stop.
    - Test it regularly in a controlled way, because an untested kill switch is not a control.
    - Give operators a simple, fast manual path that does not depend on the main application.

    Public interview guides often cite Knight Capital's 2012 trading loss as the reason these controls matter.
  </Accordion>

  <Accordion title="Q9. Design a pre-trade risk check that no outbound order can bypass.">
    **Placement:** the check sits on the only path between the order manager and the exchange gateway, so a strategy cannot route around it. Firms often add a second, simpler check at the gateway or the broker.

    **Checks:** order size and notional, price bands against a reference price (fat-finger protection), position and exposure limits, credit or margin, order and message rate, restricted lists and duplicate-order detection.

    **Design points:**

    - **Check and reserve atomically:** an approved order reserves its exposure against the limit before it is sent, and the reservation is released on cancel, reject or fill. Otherwise two orders sent at the same time can both pass and together breach the limit.
    - **Idempotency and reconciliation:** duplicated or reordered acknowledgements and fills must not double-count usage, so key every update by order ID and fill ID and reconcile against the venue.
    - **Fail closed:** if the risk state is stale, the configuration cannot be loaded, or the gateway state is ambiguous, reject new orders rather than let them through.
    - **Latency:** the check is on the critical path, so keep the limit state in memory, avoid locks shared with slow components and measure its latency percentiles.
    - **Operations:** limit changes are audited and approved, and there is an emergency path to tighten limits during an incident.

    **Follow-up:** Which way is worse to fail, false rejects or false accepts?

    → A false accept can cause unbounded loss, while a false reject loses an opportunity. Design for no false accepts, then reduce false rejects with clear limit headroom and good monitoring.
  </Accordion>

  <Accordion title={"Q10. Design a real-time position and P&L service for a market-making desk."}>
    **Inputs:** fills from every venue and broker, start-of-day positions from the books of record, live prices, and corporate actions.

    **Design points:**

    - **Event sourcing:** positions are the sum of start-of-day positions and fills, rebuilt from the fill log after any restart.
    - **Price choice:** define which price marks each instrument (mid, last trade, fair value model) and flag marks that are stale.
    - **P&L split:** separate realized from unrealized P&L, and trading P&L from start-of-day position P&L, so traders can see what today's activity did.
    - **Consistency:** each fill updates position and P&L in one step, and late or corrected fills are applied without double-counting.
    - **Reconciliation:** compare intraday positions with broker and clearing reports, and end-of-day P&L with the official books, and alert on breaks.
    - **Fan-out:** many readers (traders, risk, dashboards) should read snapshots or a stream, not query the write path.

    **Follow-up:** Live P&L and the official end-of-day P&L disagree. How do you investigate?

    → Break the difference into position differences (missing or late fills, corporate actions) and price differences (different closing prices or FX rates), and fix the source rather than adjusting the number.
  </Accordion>

  <Accordion title="Q11. Design a DMA gateway that lets clients send orders to an exchange under your firm's membership.">
    **Clarify first:** which venues and protocols (FIX or binary), how many clients, whether clients may sub-delegate access, and the latency tier. The firm is accountable for every order under its code, so safety comes before speed.

    **Architecture:**

    - **Client sessions:** one authenticated session per client, mapped to a client ID, account and limit profile. Every order carries the client identity from entry to the exchange, so any order can be traced to its sender.
    - **Risk layer on the only path:** all orders pass through the firm's pre-trade checks before the exchange gateway. Clients cannot bypass or change them. Limits are stored per client and per sub-account.
    - **Exchange connectivity:** a pool of exchange sessions with a capacity limit, such as a throttle. A fair scheduler divides capacity between clients, so one client's burst cannot starve the others.
    - **Order state:** unique client order IDs, an order state machine and a durable event log, so duplicates are rejected and the book can be rebuilt after a crash.
    - **Drop copy and reconciliation:** compare fills and open orders with the exchange record, and give clients a drop copy.

    **Controls:** an operator kill switch per client and for the whole gateway, cancel on disconnect, and fail closed when risk state or configuration is missing.

    **Follow-up 1:** A client sends orders faster than its share of the exchange throttle. What happens?

    → Apply a per-client rate limit before the shared session, and reject or queue the excess with a clear reason code. Letting the exchange reject messages makes the firm's session unpredictable for every client.

    **Follow-up 2:** How do you handle a client that sub-delegates to its own clients?

    → Require the sub-client identity on each order, apply limits at that level too, and refuse sub-delegation where the firm cannot identify and control the underlying flow. See [Direct market access (DMA)](/equities-derivatives/global/direct-market-access).
  </Accordion>
</AccordionGroup>
